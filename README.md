# FinLedger

금융 백엔드에서 발생하는 **트랜잭션, 동시성, 멱등성, 장애 복구, 대용량 처리** 문제를 직접 재현하고 해결하는 학습형 프로젝트입니다.

단순 CRUD 구현이 아니라, 실제 문제를 재현하고 원인을 분석한 뒤 해결 방법을 비교·적용하고 테스트로 검증하는 것을 목표로 합니다.

## 핵심 불변식

```text
1. account.balance >= 0

2. 내부 송금 전후 시스템 총 자산은 동일해야 한다.

3. 성공한 송금은 정확한 금액만 이동해야 한다.

4. 출금과 입금은 함께 성공하거나 함께 실패해야 한다.

5. 실제 성공한 출금 횟수와 최종 잔액은 일치해야 한다.

6. 하나의 원장 거래에서 모든 항목의 합계는 0이어야 한다.

7. 송금과 원장은 함께 기록되거나 함께 취소되어야 한다.

8. 계좌 잔액은 기준 잔액에 원장 변동액을 더한 값과 일치해야 한다.

9. 송금 취소는 원본 원장을 수정하지 않고 반대 부호의 역거래로 기록해야 한다.

10. 같은 송금은 한 번만 취소할 수 있다.

11. 같은 멱등성 키의 요청은 동시에 들어와도 송금이 한 번만 일어나야 한다.

12. 같은 멱등성 키를 다른 내용의 요청에 재사용할 수 없다.

13. 실패한 송금의 멱등성 기록은 함께 롤백되어, 같은 키로 재시도할 수 있어야 한다.
```

## 동시성 제어 한눈에 보기

현재 구조에서 동시성을 제어하는 방법과 이유를 정리했다. 락은 요청이 하나일 때도 항상 걸리며, 자바 스레드가 아니라 **DB 행**에 거는 것이라 서버가 여러 대여도 동작한다.

| 방법 | 적용 위치 | 이유 |
|---|---|---|
| **비관적 락** (`PESSIMISTIC_WRITE`, `SELECT FOR UPDATE`) | 송금, 송금 취소 | 잔액을 읽고 판단한 뒤 수정하는 흐름에서 갱신 손실을 막고, 같은 계좌의 동시 요청을 순서대로 처리 (2장) |
| **락 획득 순서 고정** (id가 작은 계좌부터) | 송금, 송금 취소 | 두 계좌를 서로 다른 순서로 잠그면 생기는 교착 상태 방지 (4장) |
| **낙관적 락** (`@Version`) | `Account` 엔티티 | 락 없이 읽고 수정하는 경로가 있어도 덮어쓰기를 막는 안전망, 비관적 락과의 비교 기반 (3장) |
| **UNIQUE 제약** | 멱등성 키, 송금–원장 연결, 역거래–원본 연결 | 처음 들어오는 요청은 행이 없어 잠글 수 없으므로, 저장 시점에 DB가 중복을 차단 (7·8장) |
| **트랜잭션 하나로 묶기** | 키 저장 + 송금 + 원장 기록 | 함께 성공하거나 함께 실패 (1·5장) |

낙관적 락 재시도(`OptimisticWithdrawRetryService`)와 락 비교용 메서드들은 3~4장 실습용이고, 실제 송금 경로는 비관적 락을 사용한다.

# 1. 트랜잭션 원자성

## 문제 상황

내부 송금 과정에서 출금 처리 후 예외가 발생하면 출금만 DB에 반영되는 부분 실패가 발생할 수 있었다.

```text
A = 100,000원
B = 0원

30,000원 송금

A 출금 완료
↓
RuntimeException 발생
↓
B 입금 실패

결과
A = 70,000원
B = 0원
```

총 자산이 `100,000원 → 70,000원`으로 감소하면서 송금 불변식이 깨졌다.

## 원인 분석

송금 과정의 여러 DB 작업이 하나의 트랜잭션으로 묶여 있지 않아, 이미 완료된 DB 변경은 이후 예외가 발생해도 자동으로 취소되지 않았다.

## 해결 방법

`TransferService`의 송금 로직에 `@Transactional`을 적용했다.

```java
@Transactional
public Transfer transfer(
        Long fromAccountId,
        Long toAccountId,
        long amount
) {
    ...
}
```

## 검증

송금 처리 중 강제로 `RuntimeException`을 발생시킨 뒤 잔액을 다시 확인했다.

```text
장애 발생 후

A = 100,000원
B = 0원

총 자산 유지 ✅
부분 반영 방지 ✅
```

## 학습 내용

- 트랜잭션
- ACID 원자성
- 커밋 / 롤백
- `@Transactional`
- 영속성 컨텍스트
- 변경 감지

# 2. 동시 출금

## 문제 상황

잔액이 10,000원인 동일 계좌에 8,000원 출금 요청 2개를 동시에 실행했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2
```

락 적용 전:

```text
성공 요청: 2
최종 잔액: 2,000원
```

실제로는 16,000원의 출금이 성공했지만 잔액에는 한 번의 출금만 반영되는 갱신 손실(Lost Update)이 발생했다.

> 이후 `Account`에 `@Version`을 도입(3장)하면서 현재 코드에서는 같은 시나리오도 낙관적 락으로 차단된다. 위 결과는 `@Version` 도입 전 커밋(`71f68e4`) 기준이며, 최신 코드로는 그대로 재현되지 않는다.

## 원인 분석

두 트랜잭션이 동시에 동일한 잔액을 조회했다.

```text
트랜잭션 A
10,000 조회
→ 8,000 출금
→ 2,000 저장

트랜잭션 B
10,000 조회
→ 8,000 출금
→ 2,000 저장
```

조회 → 계산 → 저장 사이에 다른 트랜잭션이 개입할 수 있었고, 한쪽 변경이 다른 변경을 덮어썼다.

`@Transactional`은 하나의 트랜잭션 내부 원자성을 보장하지만 서로 다른 트랜잭션 간 동시 접근까지 자동으로 제어하지는 않는다.

## 해결 방법 비교

| 방식 | 장점 | 단점 |
|---|---|---|
| 비관적 락 | 충돌을 사전에 차단하고 동작이 명확함 | 대기시간 증가, 교착 상태 가능 |
| 낙관적 락 | 락 점유가 없어 충돌이 적을 때 유리 | 충돌 시 예외 및 재시도 필요 |
| 원자적 갱신 | 단순 조건부 갱신에 효율적 | 복잡한 송금 로직 확장에 제약 |

## 선택과 근거

현재 단계에서는 `PESSIMISTIC_WRITE`를 선택했다.

계좌 잔액은 정합성이 우선되는 데이터이며, 동일 계좌에 대한 동시 변경을 DB 행 락으로 직렬화해 동작을 명확하게 확인하기 위해 비관적 락을 먼저 적용했다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
    select a
    from Account a
    where a.id = :id
""")
Optional<Account> findByIdForUpdate(Long id);
```

## 검증

같은 동시 출금 테스트를 다시 실행했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2

성공: 1건
잔액 부족 실패: 1건
최종 잔액: 2,000원
```

실제 성공한 출금 횟수와 최종 잔액이 일치함을 확인했다.

## 학습 내용

- 경쟁 상태(Race Condition)
- 갱신 손실(Lost Update)
- 비관적 락
- `SELECT FOR UPDATE`
- 트랜잭션 격리 수준

# 3. 낙관적 락

## 문제 상황

비관적 락은 조회 시점부터 행을 잠그기 때문에, 충돌이 드문 환경에서도 모든 요청이 락 대기 가능성을 안고 간다.

락을 선점하지 않고 진행하되, 저장 시점에 충돌만 감지하는 방식을 적용해 비관적 락과 동작 차이를 비교했다.

## 해결 방법

`Account`에 `@Version` 필드를 추가했다.

```java
@Version
@Column(nullable = false)
private long version;
```

수정 시 `update ... where id = ? and version = ?` 조건으로 저장되며, 그 사이 다른 트랜잭션이 먼저 커밋했다면 갱신된 행이 0건이 되어 `OptimisticLockingFailureException`이 발생한다.

## 충돌 검증

`CyclicBarrier`로 두 트랜잭션이 같은 `version`을 읽을 때까지 기다리게 한 뒤 동시에 출금했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2

성공: 1건
충돌: 1건 (OptimisticLockingFailureException)
최종 잔액: 2,000원
```

비관적 락은 두 번째 요청이 **대기 후 잔액 부족으로 실패**했지만, 낙관적 락은 두 번째 요청이 **저장 시점에 충돌로 실패**한다.

## 재시도

충돌은 예외로 끝나므로 호출하는 쪽에서 재시도해야 한다. `OptimisticWithdrawRetryService`에서 최대 3회 재시도한다.

- 재시도 반복문은 `@Transactional` 메서드 **밖**, 별도 빈에 둔다. 재시도마다 새 트랜잭션이 열리고 최신 잔액을 다시 조회한다.
- 재시도 대상은 `OptimisticLockingFailureException`뿐이다. 잔액 부족 같은 비즈니스 예외는 재시도하지 않고 그대로 던진다.
- 외부 트랜잭션 안에서 호출하면 롤백 전용이 된 트랜잭션에서 재시도가 의미 없으므로, 외부 트랜잭션 없이 호출한다.

```text
[3,000원 출금 × 3 동시 요청, 초기 잔액 10,000원]

충돌 발생 시 재시도
→ 3건 모두 성공
→ 최종 잔액: 1,000원

[8,000원 출금 × 2 동시 요청, 초기 잔액 10,000원]

성공: 1건
잔액 부족 실패: 1건 (재시도하지 않음)
최종 잔액: 2,000원
```

## 비관적 락 vs 낙관적 락

| | 비관적 락 | 낙관적 락 |
|---|---|---|
| 구현 | `findByIdForUpdate` (`SELECT FOR UPDATE`) | `@Version` + 충돌 시 재시도 |
| 충돌 시 | 대기 후 최신 값으로 진행 | 한쪽이 예외로 실패, 재시도 필요 |
| 실패 방식 | 비즈니스 규칙에 의한 실패 (잔액 부족) | 충돌 예외 → 재시도 후 비즈니스 규칙 적용 |
| 유리한 상황 | 충돌이 잦고 정합성이 최우선인 경우 | 충돌이 드물고 읽기가 많은 경우 |
| 주의점 | 락 대기, 교착 상태 | 재시도 횟수 초과, 충돌이 잦으면 헛수고 증가 |

# 4. 교착 상태

## 문제 상황

비관적 락으로 갱신 손실은 막았지만, 두 계좌를 잠그는 송금에서 락을 잡는 순서가 서로 다르면 교착 상태가 발생할 수 있다.

```text
송금 ①: 계좌 A → 계좌 B  (A 잠금 → B 잠금 시도)
송금 ②: 계좌 B → 계좌 A  (B 잠금 → A 잠금 시도)
```

출금 계좌를 먼저, 입금 계좌를 나중에 잠그도록 구현하고, 두 트랜잭션이 각각 첫 번째 계좌의 락을 잡은 상태가 되도록 첫 락 획득 직후 500ms 지연을 넣어 재현했다.

```text
시간 ↓   트랜잭션 ① (A→B)                 트랜잭션 ② (B→A)

  1      계좌 A 잠금 🔒
  2                                      계좌 B 잠금 🔒
  3      계좌 B 잠금 시도 → ② 가 보유, 대기
  4                                      계좌 A 잠금 시도 → ① 이 보유, 대기
  5      서로 상대의 락을 기다리며 진행 불가
```

## 재현 결과

```text
초기 잔액: A 100,000원 / B 100,000원
동시 요청: A → B 10,000원, B → A 20,000원

PostgreSQL: ERROR: deadlock detected

성공: 1건
실패: 1건 (CannotAcquireLockException)
```

PostgreSQL이 교착 상태를 감지해 한쪽 트랜잭션을 강제로 롤백했고, 나머지 한쪽만 성공했다.

## 원인 분석

각 트랜잭션이 첫 번째 락을 쥔 채 두 번째 락을 기다리면서 **서로 상대가 쥔 락을 기다리는 순환 대기**가 만들어졌다. 두 트랜잭션 모두 락을 놓으려면 작업을 끝내야 하는데, 다음 락을 얻지 못해 작업을 끝낼 수 없다.

계좌 하나만 잠그는 출금은 필요한 락이 하나뿐이어서 먼저 잡은 쪽이 작업을 끝내고 락을 놓으면 되므로 교착 상태가 생기지 않았다. 락을 둘 이상, 서로 다른 순서로 잡는 송금에서만 발생한다.

## 해결 방법

송금 방향과 관계없이 **항상 id가 작은 계좌부터 잠그도록** 락 획득 순서를 고정했다.

```java
Long firstLockId = Math.min(fromAccountId, toAccountId);
Long secondLockId = Math.max(fromAccountId, toAccountId);

Account first = accountRepository.findByIdForUpdate(firstLockId).orElseThrow(...);
Account second = accountRepository.findByIdForUpdate(secondLockId).orElseThrow(...);

// 이후 출금 계좌와 입금 계좌를 구분해 출금 / 입금 처리
```

서로 반대 방향의 송금도 같은 계좌에서 먼저 대기하게 되므로, 서로 다른 순서로 락을 잡는 상황이 만들어지지 않는다.

## 검증

같은 시나리오를 락 순서 고정 로직으로 다시 실행했다.

```text
초기 잔액: A 100,000원 / B 100,000원
동시 요청: A → B 10,000원, B → A 20,000원

성공: 2건
실패: 0건

A 잔액: 110,000원
B 잔액: 90,000원
총 자산: 200,000원 (송금 전후 동일)
```

교착 상태 없이 두 송금이 모두 성공했고, 총 자산이 유지됨을 확인했다.

## 학습 내용

- 교착 상태 (순환 대기)
- 락 획득 순서
- 락 순서 고정을 통한 교착 상태 예방
- PostgreSQL의 교착 상태 감지 (`deadlock detected`)

# 5. 복식 원장

## 문제 상황

지금까지의 송금은 `Account.balance`를 직접 수정하는 방식이었다.

```text
A.balance: 100,000 → 70,000
B.balance:       0 → 30,000
```

잔액은 결과만 남기 때문에, 이 잔액이 어떤 입출금을 거쳐 만들어졌는지 설명할 수 없고, 잔액이 맞는지 따로 검증할 근거도 없다.

## 설계

송금 1건마다 **원장 거래**를 만들고, 그 안에 계좌별 **원장 항목**을 남기는 복식 구조로 설계했다.

| 엔티티 | 역할 |
|---|---|
| `LedgerTransaction` (원장 거래) | 송금 1건에 대응하는 원장 묶음. `Transfer`와 1:1 (`transfer_id` 유일). 취소 거래는 7장 참고 |
| `LedgerEntry` (원장 항목) | 계좌 하나의 변동. 출금은 음수, 입금은 양수 |

```text
송금: A → B 30,000원

원장 거래
 ├─ 항목: A  -30,000
 └─ 항목: B  +30,000
 합계: 0
```

한 거래의 항목 합계는 항상 0이어야 하고, 이를 `validateBalanced()`로 검증한다. 합계가 0이 아니면 `IllegalStateException`을 던진다.

```java
public void validateBalanced(){
    if(getTotalAmount() != 0L){
        throw new IllegalStateException("원장의 합계는 0이어야 합니다.");
    }
}
```

## 송금 로직

송금과 원장 기록을 **하나의 트랜잭션**으로 묶었다.

```text
1. 락 순서 고정으로 두 계좌 잠금 (4장)
2. 송금 생성
3. 잔액 변경 (출금 / 입금)
4. 원장 거래 생성
   - 출금 계좌: -amount
   - 입금 계좌: +amount
5. 원장 균형 검증 (합계 0)
6. 원장 저장
7. 송금 상태를 SUCCESS로 변경
```

## 검증

**원장 항목 합계**

```text
출금 -30,000원 + 입금 +30,000원
→ 항목 2개, 합계 0 ✅

출금 -30,000원 + 입금 +20,000원
→ IllegalStateException("원장의 합계는 0이어야 합니다.") ✅
```

**송금 성공 시 잔액과 원장이 함께 기록됨**

```text
초기 잔액: A 100,000원 / B 0원
송금: A → B 30,000원

A 잔액: 70,000원
B 잔액: 30,000원
원장 항목: 2개
원장 합계: 0
```

**원장 기록 이후 장애 발생 시 전체 롤백**

원장까지 저장한 직후 강제로 예외를 발생시켰다.

```text
초기 잔액: A 100,000원 / B 0원
송금: A → B 30,000원 → 원장 저장 → 강제 장애

A 잔액: 100,000원
B 잔액: 0원
송금 건수: 변화 없음
원장 건수: 변화 없음
```

잔액, 송금, 원장이 모두 원래대로 롤백되어 서로 어긋나지 않음을 확인했다.

## 겪은 문제: 지연 로딩

송금 후 원장을 조회해 항목을 확인하는 테스트에서 `LazyInitializationException`이 발생했다.

```text
Cannot lazily initialize collection of role 'LedgerTransaction.entries' (no session)
```

- `LedgerTransaction.entries`는 `@OneToMany`라서 기본이 **지연 로딩**이라, 항목은 실제로 접근할 때 DB에서 가져온다.
- 테스트는 트랜잭션 밖에서 조회했고, 조회가 끝나면 세션이 닫힌다.
- 닫힌 뒤에 `getEntries()`에 접근하자 항목을 가져올 세션이 없어 실패했다.

조회 메서드에 `@EntityGraph`를 적용해 **조회할 때 항목도 함께 가져오도록** 해결했다.

```java
@EntityGraph(attributePaths = "entries")
Optional<LedgerTransaction> findByTransferId(Long transferId);
```

`left join`으로 원장 거래와 항목을 한 번에 가져오므로, 세션이 닫힌 뒤에도 항목에 접근할 수 있다.

## 학습 내용

- 복식부기와 원장
- 원장 항목 합계 불변식
- 송금과 원장을 하나의 트랜잭션으로 묶기
- 지연 로딩과 `LazyInitializationException`
- `@EntityGraph`

# 6. 원장 대사

## 문제 상황

계좌 잔액(`Account.balance`)과 원장은 **서로 다른 테이블에 따로 저장**된다. 송금 로직에서는 두 값이 함께 바뀌도록 하나의 트랜잭션으로 묶었지만, 이후에도 어긋나지 않는다고 보장할 수는 없다.

- 버그나 수동 작업으로 잔액이 직접 수정되는 경우
- 원장 기록이 누락되는 경우

어긋난 것을 **스스로 찾아낼 수단**이 없으면, 잔액이 틀려도 아무도 알아채지 못한다.

## 해결 방법

원장의 변동액을 기준으로 잔액을 다시 계산해 실제 잔액과 비교하는 대사(Reconciliation) 로직을 만들었다.

```text
기대 잔액 = 기준 잔액 + 원장 변동액
차이     = 실제 잔액 - 기대 잔액
일치 여부 = (차이 == 0)
```

- **기준 잔액**: 원장 기록을 시작하기 전의 잔액이다. 입금처럼 원장에 기록되지 않는 변동이 있어서 별도로 전달한다.
- **원장 변동액**: 해당 계좌의 원장 항목 금액 합계다. 출금은 음수, 입금은 양수라서 합치면 순변동액이 된다.

```java
@Transactional(readOnly = true)
public ReconciliationResult reconcile(Long accountId, long baseBalance) {
    Account account = accountRepository.findById(accountId)...;

    long ledgerDelta = ledgerEntryRepository.sumAmountByAccountId(accountId);
    long expectedBalance = baseBalance + ledgerDelta;
    long actualBalance = account.getBalance();
    long difference = actualBalance - expectedBalance;
    ...
}
```

결과는 `ReconciliationResult`로 돌려준다.

| 필드 | 의미 |
|---|---|
| `baseBalance` | 원장 기록 이전 기준 잔액 |
| `ledgerDelta` | 원장 항목 금액 합계 |
| `expectedBalance` | 기준 잔액 + 원장 변동액 |
| `actualBalance` | 현재 `Account.balance` |
| `difference` | 실제 잔액 - 기대 잔액 |
| `matched` | 일치 여부 |

### 원장 변동액 조회

```java
@Query("select coalesce(sum(le.amount), 0) from LedgerEntry le where le.account.id = :accountId")
long sumAmountByAccountId(@Param("accountId") Long accountId);
```

`SUM`은 합칠 행이 없으면 `0`이 아니라 `NULL`을 반환한다. 원장 이력이 없는 계좌에서도 기본형 `long`으로 받을 수 있도록 `COALESCE`로 `0`으로 바꿨다.

## 검증

송금 후 잔액을 강제로 틀어 놓고, 대사가 불일치를 찾아내는지 확인했다.

```text
초기: A 100,000원 입금 (기준 잔액 100,000원)
송금: A → B 30,000원
      → A 잔액 70,000원, 원장 변동액 -30,000원

장애 주입: A 잔액을 70,000원 → 60,000원으로 강제 변경

대사 결과
기대 잔액: 70,000원
실제 잔액: 60,000원
차이: -10,000원
일치 여부: 불일치 ✅
```

원장 기준으로 70,000원이어야 하는데 실제 잔액이 60,000원이라는 것을 찾아내고, 얼마가 어긋났는지(-10,000원)까지 알 수 있다.

## 학습 내용

- 대사(Reconciliation)
- 기대 잔액과 실제 잔액 비교
- 집계 쿼리와 `COALESCE`
- 장애 주입을 통한 불일치 탐지 검증

# 7. 역거래 (송금 취소)

## 문제 상황

송금이 한 번 성공하면 되돌릴 방법이 없었다. 취소를 직접 구현한다고 하면 두 가지 방법이 떠오른다.

| 방식 | 문제 |
|---|---|
| 원본 원장을 삭제하거나 수정 | 이력이 사라져서 무슨 일이 있었는지 추적할 수 없다 |
| 잔액만 직접 되돌림 | 원장과 잔액이 어긋나 6장의 대사에서 불일치로 잡힌다 |

## 해결 방법

원본 원장은 그대로 두고, **반대 부호의 새 원장 거래(역거래)를 추가**하는 방식으로 취소를 구현했다.

```text
원본 거래   A -30,000 / B +30,000   (합계 0)
역거래      A +30,000 / B -30,000   (합계 0)
─────────────────────────────────
두 거래를 합친 순변동: A 0, B 0
```

### 원장 거래 유형

원장 거래가 두 종류가 되었으므로 `type`으로 구분하고, 역거래는 원본을 `reversalOf`로 가리키게 했다.

| | 일반 송금 원장 | 역거래 원장 |
|---|---|---|
| `type` | `TRANSFER` | `REVERSAL` |
| `transfer` | 송금 | 없음 (`NULL`) |
| `reversalOf` | 없음 (`NULL`) | 원본 원장 거래 |

역거래는 새 송금이 아니라 기존 거래를 되돌리는 거래라서 자신의 `Transfer`가 없다. 그래서 `transfer`의 `nullable = false`를 제거했다.

### 정적 팩터리 메서드

두 종류의 원장 거래를 만드는 방식이 생겼으므로, 생성자 대신 **의도가 드러나는 이름의 정적 팩터리 메서드**로 만들도록 했다.

```java
LedgerTransaction.forTransfer(transfer, LocalDateTime.now());     // 송금 원장
LedgerTransaction.reversalOf(original, LocalDateTime.now());      // 역거래 원장
```

- 각 메서드가 `type`, `transfer`, `reversalOf`의 올바른 조합을 한 곳에서 세팅한다.
- 기본 생성자는 `protected`로 두고 옛 public 생성자는 삭제해서, `type`을 빠뜨린 원장 거래를 만드는 코드는 **컴파일 단계에서 불가능**하게 했다.

### 취소 흐름

`ReversalService.reverse(transferId)`가 하나의 트랜잭션에서 처리한다.

```text
1. 송금과 원본 원장 조회
2. 이미 취소된 거래인지 확인 (중복 취소 방지)
3. 두 계좌를 id 순으로 잠금 (4장의 락 순서 고정과 동일)
4. 잔액 되돌리기
   - 받은 계좌에서 출금
   - 보낸 계좌에 입금
5. 역거래 원장 생성: LedgerTransaction.reversalOf(original, now)
6. 원본 항목의 부호를 뒤집어 역거래 항목으로 추가
7. 원장 균형 검증 (합계 0)
8. 역거래 저장, 송금 상태를 REVERSED로 변경
```

### 중복 취소 방지

같은 송금을 두 번 취소하면 잔액이 두 번 되돌아가므로 두 겹으로 막았다.

- 코드: `existsByReversalOfId`로 이미 역거래가 있으면 예외
- DB: `reversal_of_id`에 유일 제약

송금 상태에는 `REVERSED`를 추가했고, `Transfer.reverse()`는 성공한 송금(`SUCCESS`)에서만 동작하도록 했다.

## 검증

**송금 취소**

```text
초기: A 100,000원 / B 0원
송금: A → B 30,000원
취소: 역거래 실행

A 잔액: 100,000원
B 잔액: 0원
총 자산: 100,000원
송금 상태: REVERSED
```

**중복 취소 방지**

```text
같은 송금을 두 번 취소 시도
→ IllegalStateException("이미 취소된 거래입니다.")
```

## 겪은 문제: 컬럼 추가와 `type` 누락

**1) `NOT NULL` 컬럼 추가 실패**

`type`을 `nullable = false`로 추가하자 테스트에서 다음 오류가 났다.

```text
alter table ledger_transactions add column type varchar(255) not null ...
ERROR: column "type" of relation "ledger_transactions" contains null values

→ 이후 insert 시: column "type" of relation "ledger_transactions" does not exist
```

- `ddl-auto: update`가 기존 행이 있는 테이블에 기본값 없는 `NOT NULL` 컬럼을 추가하려다 실패했다.
- 이 실패는 경고로만 남고 애플리케이션은 계속 떠서, 컬럼이 없는 상태로 insert 시점에 오류가 났다.
- 해결하려면 기존 행에 값을 채우거나(백필) 스키마를 새로 만들어야 한다. 운영 환경에서는 마이그레이션 도구로 단계적으로 적용해야 하는 이유이기도 하다.

**2) 옛 생성자가 `type`을 채우지 않음**

컬럼이 생긴 뒤에는 송금에서 `type`이 `null`로 들어가 `NOT NULL` 제약 위반이 났다. 송금 로직이 `type`을 채우지 않는 옛 생성자를 계속 쓰고 있었기 때문이다. 송금 로직을 `forTransfer`로 바꾸고 옛 생성자를 삭제해 해결했다.

## 학습 내용

- 역거래 (원본을 수정하지 않고 반대 부호로 추가)
- 원장은 덧붙이기만 한다는 원칙
- 정적 팩터리 메서드
- 원장 거래 유형과 연관 관계 (`nullable` 변경)
- `ddl-auto: update`의 한계와 마이그레이션

# 8. 멱등성

## 문제 상황

송금 요청이 실패한 것처럼 보여서 클라이언트가 **같은 요청을 다시 보내는** 경우가 있다.

- 서버는 처리했는데 응답이 중간에 끊겨 클라이언트가 실패로 오해하고 재시도
- 사용자가 버튼을 두 번 누름

요청마다 새 송금으로 처리하면 같은 요청이 두 번 반영되어 **이중 송금**이 된다.

## 해결 방법

클라이언트가 요청마다 고유한 **멱등성 키**를 보내고, 서버는 키와 처리 결과를 `IdempotencyRecord`에 기록한다. 같은 키가 다시 오면 새로 처리하지 않고 **처음 처리한 결과를 그대로 돌려준다.**

| 필드 | 의미 |
|---|---|
| `idempotencyKey` | 요청 식별 키 (유일) |
| `fromAccountId`, `toAccountId`, `amount` | 처음 요청의 내용 |
| `transfer` | 처리 결과 (완료 후 연결) |

### UNIQUE 제약

키 컬럼에 `UNIQUE(idempotency_key)`를 걸었다. 코드에서 "이 키가 있는지 조회한 뒤 없으면 처리"하는 것만으로는 동시 요청을 막을 수 없기 때문이다.

```text
시간 ↓   요청 ①                         요청 ②

  1      키 조회 → 없음
  2                                      키 조회 → 없음
  3      송금 처리, 키 저장
  4                                      송금 처리, 키 저장   ← 이중 송금
```

조회와 저장 사이에 다른 요청이 끼어드는 문제(2장의 갱신 손실과 같은 구조)이고, 처음 들어온 키는 아직 행이 없어 `FOR UPDATE`로 잠글 대상도 없다. `UNIQUE` 제약을 두면 같은 키의 저장을 DB가 마지막에 막아 준다.

```text
  3      키 저장 성공 ✅
  4                                      키 저장 시도 → UNIQUE 위반 ❌
```

### 트랜잭션 분리

`UNIQUE` 위반이 난 트랜잭션은 이미 롤백 대상이라, 같은 트랜잭션 안에서 예외를 잡아 기존 결과를 조회할 수 없다. PostgreSQL은 오류가 난 트랜잭션이 끝나기 전까지 다른 쿼리를 받지 않고, Spring도 해당 트랜잭션을 롤백 전용으로 표시하기 때문이다.

그래서 **트랜잭션을 수행하는 Bean과 예외를 처리하는 Bean을 분리**했다.

```text
[IdempotentTransferService]   ← @Transactional 없음, 예외를 잡을 깨끗한 곳
    │
    ├─ try:    [IdempotentTransferProcessor]   ← 트랜잭션
    │             키 저장(flush) → 송금 → 키에 결과 연결
    │
    └─ catch (UNIQUE 위반):
                 트랜잭션 밖에서 키를 다시 조회 → 기존 결과 반환
```

```java
// IdempotentTransferService (트랜잭션 없음)
try {
    return processor.process(key, fromAccountId, toAccountId, amount);
} catch (DataIntegrityViolationException e) {
    // 실패한 트랜잭션 밖에서 기록을 다시 조회
    IdempotencyRecord record = idempotencyRecordRepository.findByKey(key).orElseThrow(() -> e);
    return resolveExisting(record, fromAccountId, toAccountId, amount);
}
```

```java
// IdempotentTransferProcessor
@Transactional
public Transfer process(String key, Long fromAccountId, Long toAccountId, long amount) {
    IdempotencyRecord record = new IdempotencyRecord(key, fromAccountId, toAccountId, amount);
    idempotencyRecordRepository.saveAndFlush(record);   // UNIQUE를 즉시 확인

    Transfer transfer = transferService.transfer(fromAccountId, toAccountId, amount);
    record.complete(transfer);
    return transfer;
}
```

`@Transactional`은 프록시로 동작하므로 같은 클래스 안의 호출로는 트랜잭션이 만들어지지 않는다. 그래서 반드시 다른 Bean을 호출해야 한다(3장의 재시도와 같은 이유).

### 같은 키, 다른 요청

기존 결과를 돌려주기 전에 **요청 내용이 처음과 같은지** 비교한다. 같은 키로 금액이나 계좌가 다른 요청이 오면 이전 결과를 돌려주지 않고 `IdempotencyKeyConflictException`으로 거부한다.

```text
키 "abc": A → B 30,000원 (처리됨)
키 "abc": A → B 30,000원 → 이전 결과 반환
키 "abc": A → B 50,000원 → IdempotencyKeyConflictException
```

### 실패한 송금은 키도 함께 롤백

키 저장, 송금, 결과 연결을 **하나의 트랜잭션**으로 묶었기 때문에, 송금이 실패하면(예: 잔액 부족) 멱등성 기록도 함께 롤백된다. 실패한 요청의 키가 "처리됨"으로 남아 같은 키로 재시도할 수 없게 되는 일이 없다.

### 입력 검증

DB에 접근하기 전에 잘못된 요청을 먼저 거부한다(`IllegalArgumentException`).

- 멱등성 키: null, 공백, 128자 초과
- 계좌 ID: null
- 송금 금액: 0원 이하

키 컬럼도 길이를 128자로 제한했다.

## 검증

**같은 키의 순차 요청**

```text
초기: A 100,000원 / B 0원
같은 키로 A → B 30,000원 요청 2번

두 요청이 같은 송금(Transfer) 반환
A 잔액: 70,000원
B 잔액: 30,000원
송금 건수 +1, 원장 건수 +1
```

**같은 키, 다른 요청**

```text
같은 키로 30,000원 요청 후 50,000원 요청
→ IdempotencyKeyConflictException
```

**같은 키의 동시 요청**

```text
같은 키로 A → B 30,000원 요청 2개를 동시에 실행

두 요청이 같은 송금(Transfer) 반환
A 잔액: 70,000원
B 잔액: 30,000원
```

**송금 실패 후 같은 키로 재시도**

```text
초기: A 10,000원 / B 0원
키 K로 A → B 30,000원 요청 → 잔액 부족으로 실패

멱등성 기록: 없음 (함께 롤백)
원장 건수: 변화 없음

A에 30,000원 충전 후 같은 키 K로 같은 요청 재시도
→ 성공
A 잔액: 10,000원
B 잔액: 30,000원
송금 건수 +1, 원장 건수 +1
```

**송금 성공 후 응답을 받지 못해 재전송**

```text
키 K로 A → B 30,000원 요청 (성공, 응답은 받지 못했다고 가정)
같은 요청 재전송

새 송금이 아니라 기존 송금(Transfer) 반환
A 잔액: 70,000원
B 잔액: 30,000원
송금 건수 +1, 원장 건수 +1
```

**같은 키로 서로 다른 요청을 동시에**

```text
같은 키 K로 A → B 30,000원 요청과 40,000원 요청을 동시에 실행

성공: 1건
나머지: IdempotencyKeyConflictException
잔액: 성공한 요청의 금액만 반영
송금 건수 +1, 원장 건수 +1
```

## 겪은 문제

**1) 락 조회 메서드를 트랜잭션 없이 호출**

검증 단계에서 `findByIdForUpdate`를 그대로 호출했더니 `TransactionRequiredException: No active transaction`이 발생했다. `FOR UPDATE`는 트랜잭션 안에서만 의미가 있어 트랜잭션이 없으면 JPA가 거부한다. 값을 읽기만 하는 검증이라 락이 필요 없어서 `findById`로 바꿔 해결했다.

**2) 고정 키가 이전 실행의 기록과 충돌**

테스트의 멱등성 키를 고정 문자열로 썼더니, 두 번째 실행부터 `IdempotencyKeyConflictException`이 발생했다.

- 이전 실행이 남긴 기록(다른 계좌 id)이 DB에 그대로 있었다.
- 같은 키로 다른 계좌 요청이 왔으므로 서비스가 의도대로 충돌로 거부한 것이다.

테스트마다 `UUID`를 붙여 고유한 키를 쓰도록 바꿔 해결했다. 실제 클라이언트도 요청마다 고유한 키를 보낸다.

# 9. 통합 검증

앞에서 만든 기능들이 따로 동작하는 것이 아니라 **한 흐름 안에서 함께 맞물려 동작**하는지 통합 테스트로 확인했다. 실제 요청 진입점인 멱등성 서비스(`IdempotentTransferService`)를 통해 호출한다.

## 송금부터 역거래까지 정합성 유지

```text
1. 송금 (멱등성 서비스)              A → B 30,000원
2. 같은 키로 재전송                   → 같은 송금(Transfer) 반환, 송금 건수 +1
3. 원본 원장 확인                    항목 2개 (A -30,000 / B +30,000), 합계 0
4. 송금 직후 대사                     A, B 모두 일치
5. 역거래                            송금 취소
6. 역거래 원장 확인                   항목 2개, 합계 0
                                     원본 + 역거래 합계 0
7. 최종 잔액                         A 100,000원 / B 0원 (총 자산 100,000원)
8. 역거래 후 대사                     A, B 모두 일치
9. 상태와 건수                       송금 상태 REVERSED
                                     송금 +1건, 원장 +2건 (원본 1 + 역거래 1)
10. 같은 송금을 다시 역거래           → IllegalStateException
```

- 원장 항목이 2개인 것은 재전송 때문이 아니라 복식 원장에서 **한 거래가 출금 항목과 입금 항목을 함께 가지기 때문**이다.
- 재전송은 송금이 실행되지 않으므로 원장에도 아무것도 추가되지 않는다.
- 대사의 기준 잔액은 원장 기록 이전 잔액(A 100,000원, B 0원)이다.

## 수취 계좌 잔액 부족 시 역거래 롤백

송금된 돈을 수취 계좌가 이미 써버려서 취소할 수 없는 경우, 실패한 취소가 부분적으로 반영되지 않는지 확인했다.

```text
초기: A 100,000원
A → B 30,000원 송금
B → C 25,000원 송금   → B 잔액 5,000원

A → B 송금 취소 시도 (B가 30,000원을 돌려줄 수 없음)
→ 실패

A 잔액: 70,000원
B 잔액: 5,000원
C 잔액: 25,000원
역거래 원장: 생성되지 않음
원장 건수: 변화 없음
원본 송금 상태: SUCCESS (REVERSED로 바뀌지 않음)
```

실패한 취소는 잔액, 원장, 송금 상태 어느 쪽에도 흔적을 남기지 않고 전체가 롤백된다.

- 잔액과 원장을 독립적으로 교차 검증하는 대사

- 정상 내부 송금

- 내부 송금의 원장 항목 합계가 0임을 검증
- 원장 항목 합계가 0이 아니면 검증 시 예외 발생

- 계좌 잔액과 원장이 다르면 불일치 탐지 (기대 잔액 / 실제 잔액 / 차이 검증)

### 송금 취소

- 성공한 송금을 역거래로 취소 (잔액 복구, 송금 상태 `REVERSED`, 총 자산 보존)
- 같은 송금을 두 번 취소할 수 없음

### 멱등성

- 같은 멱등성 키의 동일 요청은 한 번만 송금
- 같은 멱등성 키를 다른 요청에 재사용할 수 없음
- 같은 멱등성 키의 동시 요청도 한 번만 송금
- 송금 실패 시 멱등성 기록이 롤백되어 같은 키로 재시도 가능
- 송금 성공 후 응답 유실로 재전송해도 중복 출금되지 않음
- 같은 키의 서로 다른 요청을 동시에 보내면 하나만 성공

### 통합

- 송금, 재전송, 원장, 대사, 역거래, 중복 역거래 차단까지 한 흐름의 정합성 유지
- 수취 계좌 잔액이 부족하면 역거래가 롤백되고 잔액·원장·송금 상태가 변하지 않음
