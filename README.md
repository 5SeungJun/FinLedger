# FinLedger

금융 백엔드에서 발생하는 **트랜잭션, 동시성, 멱등성, 장애 복구, 대용량 처리** 문제를 직접 재현하고 해결하는 학습형 프로젝트입니다.

단순 CRUD 구현이 아니라, 실제 문제를 재현하고 원인을 분석한 뒤 해결 방법을 비교·적용하고 테스트로 검증하는 것을 목표로 합니다.

# 1. 트랜잭션 원자성

## 문제 상황

내부 송금 과정에서 출금 처리 후 예외가 발생하면 출금만 DB에 반영되는 부분 실패가 발생할 수 있었다.

```text
A = 100,000원
B = 0원

30,000원 송금

A 출금 완료
↓
RuntimeException 발생
↓
B 입금 실패

결과
A = 70,000원
B = 0원
```

총 자산이 `100,000원 → 70,000원`으로 감소하면서 송금 불변식이 깨졌다.

## 원인 분석

송금 과정의 여러 DB 작업이 하나의 트랜잭션으로 묶여 있지 않아, 이미 완료된 DB 변경은 이후 예외가 발생해도 자동으로 취소되지 않았다.

## 해결 방법

`TransferService`의 송금 로직에 `@Transactional`을 적용했다.

```java
@Transactional
public Transfer transfer(
        Long fromAccountId,
        Long toAccountId,
        long amount
) {
    ...
}
```

## 검증

송금 처리 중 강제로 `RuntimeException`을 발생시킨 뒤 잔액을 다시 확인했다.

```text
장애 발생 후

A = 100,000원
B = 0원

총 자산 유지 ✅
부분 반영 방지 ✅
```

## 학습 내용

- 트랜잭션
- ACID 원자성
- 커밋 / 롤백
- `@Transactional`
- 영속성 컨텍스트
- 변경 감지

# 2. 동시 출금

## 문제 상황

잔액이 10,000원인 동일 계좌에 8,000원 출금 요청 2개를 동시에 실행했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2
```

락 적용 전:

```text
성공 요청: 2
최종 잔액: 2,000원
```

실제로는 16,000원의 출금이 성공했지만 잔액에는 한 번의 출금만 반영되는 갱신 손실(Lost Update)이 발생했다.

> 이후 `Account`에 `@Version`을 도입(3장)하면서 현재 코드에서는 같은 시나리오도 낙관적 락으로 차단된다. 위 결과는 `@Version` 도입 전 커밋(`71f68e4`) 기준이며, 최신 코드로는 그대로 재현되지 않는다.

## 원인 분석

두 트랜잭션이 동시에 동일한 잔액을 조회했다.

```text
트랜잭션 A
10,000 조회
→ 8,000 출금
→ 2,000 저장

트랜잭션 B
10,000 조회
→ 8,000 출금
→ 2,000 저장
```

조회 → 계산 → 저장 사이에 다른 트랜잭션이 개입할 수 있었고, 한쪽 변경이 다른 변경을 덮어썼다.

`@Transactional`은 하나의 트랜잭션 내부 원자성을 보장하지만 서로 다른 트랜잭션 간 동시 접근까지 자동으로 제어하지는 않는다.

## 해결 방법 비교

| 방식 | 장점 | 단점 |
|---|---|---|
| 비관적 락 | 충돌을 사전에 차단하고 동작이 명확함 | 대기시간 증가, 교착 상태 가능 |
| 낙관적 락 | 락 점유가 없어 충돌이 적을 때 유리 | 충돌 시 예외 및 재시도 필요 |
| 원자적 갱신 | 단순 조건부 갱신에 효율적 | 복잡한 송금 로직 확장에 제약 |

## 선택과 근거

현재 단계에서는 `PESSIMISTIC_WRITE`를 선택했다.

계좌 잔액은 정합성이 우선되는 데이터이며, 동일 계좌에 대한 동시 변경을 DB 행 락으로 직렬화해 동작을 명확하게 확인하기 위해 비관적 락을 먼저 적용했다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("""
    select a
    from Account a
    where a.id = :id
""")
Optional<Account> findByIdForUpdate(Long id);
```

## 검증

같은 동시 출금 테스트를 다시 실행했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2

성공: 1건
잔액 부족 실패: 1건
최종 잔액: 2,000원
```

실제 성공한 출금 횟수와 최종 잔액이 일치함을 확인했다.

## 학습 내용

- 경쟁 상태(Race Condition)
- 갱신 손실(Lost Update)
- 비관적 락
- `SELECT FOR UPDATE`
- 트랜잭션 격리 수준

# 3. 낙관적 락

## 문제 상황

비관적 락은 조회 시점부터 행을 잠그기 때문에, 충돌이 드문 환경에서도 모든 요청이 락 대기 가능성을 안고 간다.

락을 선점하지 않고 진행하되, 저장 시점에 충돌만 감지하는 방식을 적용해 비관적 락과 동작 차이를 비교했다.

## 해결 방법

`Account`에 `@Version` 필드를 추가했다.

```java
@Version
@Column(nullable = false)
private long version;
```

수정 시 `update ... where id = ? and version = ?` 조건으로 저장되며, 그 사이 다른 트랜잭션이 먼저 커밋했다면 갱신된 행이 0건이 되어 `OptimisticLockingFailureException`이 발생한다.

## 충돌 검증

`CyclicBarrier`로 두 트랜잭션이 같은 `version`을 읽을 때까지 기다리게 한 뒤 동시에 출금했다.

```text
초기 잔액: 10,000원
동시 요청: 8,000원 출금 × 2

성공: 1건
충돌: 1건 (OptimisticLockingFailureException)
최종 잔액: 2,000원
```

비관적 락은 두 번째 요청이 **대기 후 잔액 부족으로 실패**했지만, 낙관적 락은 두 번째 요청이 **저장 시점에 충돌로 실패**한다.

## 재시도

충돌은 예외로 끝나므로 호출하는 쪽에서 재시도해야 한다. `OptimisticWithdrawRetryService`에서 최대 3회 재시도한다.

- 재시도 반복문은 `@Transactional` 메서드 **밖**, 별도 빈에 둔다. 재시도마다 새 트랜잭션이 열리고 최신 잔액을 다시 조회한다.
- 재시도 대상은 `OptimisticLockingFailureException`뿐이다. 잔액 부족 같은 비즈니스 예외는 재시도하지 않고 그대로 던진다.
- 외부 트랜잭션 안에서 호출하면 롤백 전용이 된 트랜잭션에서 재시도가 의미 없으므로, 외부 트랜잭션 없이 호출한다.

```text
[3,000원 출금 × 3 동시 요청, 초기 잔액 10,000원]

충돌 발생 시 재시도
→ 3건 모두 성공
→ 최종 잔액: 1,000원

[8,000원 출금 × 2 동시 요청, 초기 잔액 10,000원]

성공: 1건
잔액 부족 실패: 1건 (재시도하지 않음)
최종 잔액: 2,000원
```

## 비관적 락 vs 낙관적 락

| | 비관적 락 | 낙관적 락 |
|---|---|---|
| 구현 | `findByIdForUpdate` (`SELECT FOR UPDATE`) | `@Version` + 충돌 시 재시도 |
| 충돌 시 | 대기 후 최신 값으로 진행 | 한쪽이 예외로 실패, 재시도 필요 |
| 실패 방식 | 비즈니스 규칙에 의한 실패 (잔액 부족) | 충돌 예외 → 재시도 후 비즈니스 규칙 적용 |
| 유리한 상황 | 충돌이 잦고 정합성이 최우선인 경우 | 충돌이 드물고 읽기가 많은 경우 |
| 주의점 | 락 대기, 교착 상태 | 재시도 횟수 초과, 충돌이 잦으면 헛수고 증가 |

## 학습 내용

- 낙관적 락
- `@Version`
- 충돌 감지와 재시도
- 재시도 로직을 트랜잭션 밖에 두는 이유
- 비관적 락과의 동작 차이

# 4. 교착 상태

## 문제 상황

비관적 락으로 갱신 손실은 막았지만, 두 계좌를 잠그는 송금에서 락을 잡는 순서가 서로 다르면 교착 상태가 발생할 수 있다.

```text
송금 ①: 계좌 A → 계좌 B  (A 잠금 → B 잠금 시도)
송금 ②: 계좌 B → 계좌 A  (B 잠금 → A 잠금 시도)
```

출금 계좌를 먼저, 입금 계좌를 나중에 잠그도록 구현하고, 두 트랜잭션이 각각 첫 번째 계좌의 락을 잡은 상태가 되도록 첫 락 획득 직후 500ms 지연을 넣어 재현했다.

```text
시간 ↓   트랜잭션 ① (A→B)                 트랜잭션 ② (B→A)

  1      계좌 A 잠금 🔒
  2                                      계좌 B 잠금 🔒
  3      계좌 B 잠금 시도 → ② 가 보유, 대기
  4                                      계좌 A 잠금 시도 → ① 이 보유, 대기
  5      서로 상대의 락을 기다리며 진행 불가
```

## 재현 결과

```text
초기 잔액: A 100,000원 / B 100,000원
동시 요청: A → B 10,000원, B → A 20,000원

PostgreSQL: ERROR: deadlock detected

성공: 1건
실패: 1건 (CannotAcquireLockException)
```

PostgreSQL이 교착 상태를 감지해 한쪽 트랜잭션을 강제로 롤백했고, 나머지 한쪽만 성공했다.

## 원인 분석

각 트랜잭션이 첫 번째 락을 쥔 채 두 번째 락을 기다리면서 **서로 상대가 쥔 락을 기다리는 순환 대기**가 만들어졌다. 두 트랜잭션 모두 락을 놓으려면 작업을 끝내야 하는데, 다음 락을 얻지 못해 작업을 끝낼 수 없다.

계좌 하나만 잠그는 출금은 필요한 락이 하나뿐이어서 먼저 잡은 쪽이 작업을 끝내고 락을 놓으면 되므로 교착 상태가 생기지 않았다. 락을 둘 이상, 서로 다른 순서로 잡는 송금에서만 발생한다.

## 해결 방법

송금 방향과 관계없이 **항상 id가 작은 계좌부터 잠그도록** 락 획득 순서를 고정했다.

```java
Long firstLockId = Math.min(fromAccountId, toAccountId);
Long secondLockId = Math.max(fromAccountId, toAccountId);

Account first = accountRepository.findByIdForUpdate(firstLockId).orElseThrow(...);
Account second = accountRepository.findByIdForUpdate(secondLockId).orElseThrow(...);

// 이후 출금 계좌와 입금 계좌를 구분해 출금 / 입금 처리
```

서로 반대 방향의 송금도 같은 계좌에서 먼저 대기하게 되므로, 서로 다른 순서로 락을 잡는 상황이 만들어지지 않는다.

## 검증

같은 시나리오를 락 순서 고정 로직으로 다시 실행했다.

```text
초기 잔액: A 100,000원 / B 100,000원
동시 요청: A → B 10,000원, B → A 20,000원

성공: 2건
실패: 0건

A 잔액: 110,000원
B 잔액: 90,000원
총 자산: 200,000원 (송금 전후 동일)
```

교착 상태 없이 두 송금이 모두 성공했고, 총 자산이 유지됨을 확인했다.

## 학습 내용

- 교착 상태 (순환 대기)
- 락 획득 순서
- 락 순서 고정을 통한 교착 상태 예방
- PostgreSQL의 교착 상태 감지 (`deadlock detected`)

# 5. 복식 원장

## 문제 상황

지금까지의 송금은 `Account.balance`를 직접 수정하는 방식이었다.

```text
A.balance: 100,000 → 70,000
B.balance:       0 → 30,000
```

잔액은 결과만 남기 때문에, 이 잔액이 어떤 입출금을 거쳐 만들어졌는지 설명할 수 없고, 잔액이 맞는지 따로 검증할 근거도 없다.

## 설계

송금 1건마다 **원장 거래**를 만들고, 그 안에 계좌별 **원장 항목**을 남기는 복식 구조로 설계했다.

| 엔티티 | 역할 |
|---|---|
| `LedgerTransaction` (원장 거래) | 송금 1건에 대응하는 원장 묶음. `Transfer`와 1:1 (`transfer_id` 유일) |
| `LedgerEntry` (원장 항목) | 계좌 하나의 변동. 출금은 음수, 입금은 양수 |

```text
송금: A → B 30,000원

원장 거래
 ├─ 항목: A  -30,000
 └─ 항목: B  +30,000
 합계: 0
```

한 거래의 항목 합계는 항상 0이어야 하고, 이를 `validateBalanced()`로 검증한다. 합계가 0이 아니면 `IllegalStateException`을 던진다.

```java
public void validateBalanced(){
    if(getTotalAmount() != 0L){
        throw new IllegalStateException("원장의 합계는 0이어야 합니다.");
    }
}
```

## 송금 로직

송금과 원장 기록을 **하나의 트랜잭션**으로 묶었다.

```text
1. 락 순서 고정으로 두 계좌 잠금 (4장)
2. 송금 생성
3. 잔액 변경 (출금 / 입금)
4. 원장 거래 생성
   - 출금 계좌: -amount
   - 입금 계좌: +amount
5. 원장 균형 검증 (합계 0)
6. 원장 저장
7. 송금 상태를 SUCCESS로 변경
```

## 검증

**원장 항목 합계**

```text
출금 -30,000원 + 입금 +30,000원
→ 항목 2개, 합계 0 ✅

출금 -30,000원 + 입금 +20,000원
→ IllegalStateException("원장의 합계는 0이어야 합니다.") ✅
```

**송금 성공 시 잔액과 원장이 함께 기록됨**

```text
초기 잔액: A 100,000원 / B 0원
송금: A → B 30,000원

A 잔액: 70,000원
B 잔액: 30,000원
원장 항목: 2개
원장 합계: 0
```

**원장 기록 이후 장애 발생 시 전체 롤백**

원장까지 저장한 직후 강제로 예외를 발생시켰다.

```text
초기 잔액: A 100,000원 / B 0원
송금: A → B 30,000원 → 원장 저장 → 강제 장애

A 잔액: 100,000원
B 잔액: 0원
송금 건수: 변화 없음
원장 건수: 변화 없음
```

잔액, 송금, 원장이 모두 원래대로 롤백되어 서로 어긋나지 않음을 확인했다.

## 겪은 문제: 지연 로딩

송금 후 원장을 조회해 항목을 확인하는 테스트에서 `LazyInitializationException`이 발생했다.

```text
Cannot lazily initialize collection of role 'LedgerTransaction.entries' (no session)
```

- `LedgerTransaction.entries`는 `@OneToMany`라서 기본이 **지연 로딩**이라, 항목은 실제로 접근할 때 DB에서 가져온다.
- 테스트는 트랜잭션 밖에서 조회했고, 조회가 끝나면 세션이 닫힌다.
- 닫힌 뒤에 `getEntries()`에 접근하자 항목을 가져올 세션이 없어 실패했다.

조회 메서드에 `@EntityGraph`를 적용해 **조회할 때 항목도 함께 가져오도록** 해결했다.

```java
@EntityGraph(attributePaths = "entries")
Optional<LedgerTransaction> findByTransferId(Long transferId);
```

`left join`으로 원장 거래와 항목을 한 번에 가져오므로, 세션이 닫힌 뒤에도 항목에 접근할 수 있다.

# 6. 원장 대사

## 문제 상황

계좌 잔액(`Account.balance`)과 원장은 **서로 다른 테이블에 따로 저장**된다. 송금 로직에서는 두 값이 함께 바뀌도록 하나의 트랜잭션으로 묶었지만, 이후에도 어긋나지 않는다고 보장할 수는 없다.

- 버그나 수동 작업으로 잔액이 직접 수정되는 경우
- 원장 기록이 누락되는 경우

어긋난 것을 **스스로 찾아낼 수단**이 없으면, 잔액이 틀려도 아무도 알아채지 못한다.

## 해결 방법

원장의 변동액을 기준으로 잔액을 다시 계산해 실제 잔액과 비교하는 대사(Reconciliation) 로직을 만들었다.

```text
기대 잔액 = 기준 잔액 + 원장 변동액
차이     = 실제 잔액 - 기대 잔액
일치 여부 = (차이 == 0)
```

- **기준 잔액**: 원장 기록을 시작하기 전의 잔액이다. 입금처럼 원장에 기록되지 않는 변동이 있어서 별도로 전달한다.
- **원장 변동액**: 해당 계좌의 원장 항목 금액 합계다. 출금은 음수, 입금은 양수라서 합치면 순변동액이 된다.

```java
@Transactional(readOnly = true)
public ReconciliationResult reconcile(Long accountId, long baseBalance) {
    Account account = accountRepository.findById(accountId)...;

    long ledgerDelta = ledgerEntryRepository.sumAmountByAccountId(accountId);
    long expectedBalance = baseBalance + ledgerDelta;
    long actualBalance = account.getBalance();
    long difference = actualBalance - expectedBalance;
    ...
}
```

결과는 `ReconciliationResult`로 돌려준다.

| 필드 | 의미 |
|---|---|
| `baseBalance` | 원장 기록 이전 기준 잔액 |
| `ledgerDelta` | 원장 항목 금액 합계 |
| `expectedBalance` | 기준 잔액 + 원장 변동액 |
| `actualBalance` | 현재 `Account.balance` |
| `difference` | 실제 잔액 - 기대 잔액 |
| `matched` | 일치 여부 |

### 원장 변동액 조회

```java
@Query("select coalesce(sum(le.amount), 0) from LedgerEntry le where le.account.id = :accountId")
long sumAmountByAccountId(@Param("accountId") Long accountId);
```

`SUM`은 합칠 행이 없으면 `0`이 아니라 `NULL`을 반환한다. 원장 이력이 없는 계좌에서도 기본형 `long`으로 받을 수 있도록 `COALESCE`로 `0`으로 바꿨다.

## 검증

송금 후 잔액을 강제로 틀어 놓고, 대사가 불일치를 찾아내는지 확인했다.

```text
초기: A 100,000원 입금 (기준 잔액 100,000원)
송금: A → B 30,000원
      → A 잔액 70,000원, 원장 변동액 -30,000원

장애 주입: A 잔액을 70,000원 → 60,000원으로 강제 변경

대사 결과
기대 잔액: 70,000원
실제 잔액: 60,000원
차이: -10,000원
일치 여부: 불일치 ✅
```

원장 기준으로 70,000원이어야 하는데 실제 잔액이 60,000원이라는 것을 찾아내고, 얼마가 어긋났는지(-10,000원)까지 알 수 있다.
